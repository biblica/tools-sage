# Python maintenance

This guide governs human editing of SAGE Python source. The authoritative spelling and naming rules remain in [SAGE system grammar](../architecture/SAGE-SYSTEM-GRAMMAR.md).

## Maintained Python areas

```text
system/src/sage/                 Runtime and workflow controller modules
system/tools/                         Validation, reset, audit, hardening, and release tools
system/tests/                          Executable contracts and regression coverage
```

Do not edit generated bytecode or cache directories such as `__pycache__`, coverage data, task outputs, or copied Python files inside temporary test workspaces.

## File and identifier naming

- Use `snake_case.py` for modules and scripts.
- Use `snake_case` for functions, methods, variables, internal operation values, YAML fields, and JSON fields.
- Use `PascalCase` for classes and exception types.
- Use `UPPER_SNAKE_CASE` for constants.
- Use hyphens only in literal CLI actions/options, Skill directory names, Markdown filenames, and other contracts that explicitly require them.
- Preserve canonical external values exactly, including `self_check`, `FINALIZED`, `normalized-findings.json`, project IDs, and USFM book codes.

## Required documentation

Every Python module must have:

1. A module docstring describing the file's responsibility.
2. Every class, function, method, nested function, and test procedure documented with a purpose-specific docstring.
3. A comment explaining the reason and invariant wherever a security, compatibility, transaction, path, evidence, or state rule is not obvious from the code.
4. no stale `TODO`, `FIXME`, debugging note, or generated comment.

A useful procedure docstring states at least one of these:

- what governed value is returned;
- what state transition is performed;
- what boundary is enforced;
- what side effect is permitted;
- what invalid condition is rejected;
- why the helper exists separately from its caller.

Avoid comments such as `increment the counter`, `open the file`, or `return the result`. They repeat syntax without helping a maintainer.

## Human-editing rules

- Keep one statement per line.
- Keep imports on separate, grouped lines.
- Prefer explicit intermediate variables for hashes, paths, state decisions, and validation results.
- Keep path-containment checks close to the operation they protect.
- Keep controller-owned writes behind atomic or transactional helpers.
- Do not duplicate canonical command grammar in a workflow module when the CLI parser already owns it.
- Do not bypass typed SAGE errors with generic exceptions merely to shorten code.
- Keep natural-language routing proposal-only; canonical parsing and controllers remain authoritative.
- Keep BIC and SAW operation boundaries visible in both names and comments.

## Operator-facing strings

Use U.S. English in comments, docstrings, errors, prompts, reports, and help text. Preserve exact
literals where compatibility requires them, including:

- command actions such as `workspace initialize`;
- status values such as `FINALIZED`;
- schema fields such as `normalization`;
- filenames such as `normalized-findings.json`;
- accepted natural-language synonyms such as `analyze` and `finalize`.

## Safe edit sequence

1. Reset generated state:

   ```bash
   ./system/bin/sage --settings FILE.yml workspace reset-state
   ```

2. Edit only maintained source files.
3. Parse all Python without generating bytecode:

   ```bash
   PYTHONDONTWRITEBYTECODE=1 python -m pytest -p no:cacheprovider --collect-only -q
   ```

4. Run the focused test module for the edited contract.
5. Run the full hardening command. The runner discovers all `system/tests/test_*.py` modules and fails if any discovered module is unscheduled:

   ```bash
   python system/tools/hardening.py
   ```

6. Reset generated state again.
7. Validate the populated workspace without treating resource Scripture as source-package leakage:

   ```bash
   ./system/bin/sage --settings FILE.yml --no-prompt workspace validate
   python system/tools/deep_audit.py . --mode workspace
   ```

8. Build the release. Production `build_release.py` reruns isolated hardening and accepts the package only when the hardening source-tree SHA-256 matches the exact staged tree. Extract the clean release, then run source-package checks inside that extracted copy:

   ```bash
   python system/tools/validate_package.py
   python system/tools/deep_audit.py . --mode source
   ```

9. Accept the release only after both populated-workspace and clean-source checks return zero errors and zero warnings.

## Review checklist

- [ ] The module purpose remains accurate.
- [ ] Every procedure docstring matches actual inputs, outputs, side effects, and failures.
- [ ] Comments explain reasons or invariants rather than syntax.
- [ ] Operator-facing text follows the SAGE system grammar.
- [ ] Internal `_` and external `-` forms have not been interchanged.
- [ ] No task, audit-log, cache, bytecode, coverage, temporary, or editor artifact remains.
- [ ] Relevant focused tests pass.
- [ ] Full hardening, reset, validation, and deep audit pass.
